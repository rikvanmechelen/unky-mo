# Unky Mo

Claude Code session orchestrator for MoMA workspace projects.

## Build & Run

```
make install   # Build and install to ~/go/bin/mo
./mo           # Launch TUI (auto-creates tmux session if needed)
./mo list      # List projects
./mo sessions  # List active Claude sessions
./mo restart   # Restart the running TUI, its sidebars and mo web (like ctrl+alt+r) — run after `make install`
./mo hooks install  # Install status hooks into ~/.claude/settings.json (the TUI also does this on every start)
./mo calls [dir] [--base branch|head] [--format text|json|dot] [--fail-on removed-called,…]  # The change's call graph (the Overview's Functions view) in the terminal
./mo web       # Serve the web dashboard over HTTPS (local CA; `mo web tls trust` for setup) (the TUI auto-starts it in a detached `mo-web` tmux session) (sessions, worktrees, PRs, tickets, usage) + a live chat view per session
```

## Architecture

- **Go + Bubbletea v2** TUI with charmbracelet ecosystem (lipgloss v2, bubbles v2) — imports via `charm.land/*/v2`
- **Cobra** CLI with subcommands
- **tmux** session management — TUI runs as window 0, Claude sessions as sibling windows with sidebar panes
- **Unix domain socket** at `/tmp/unky-mo.sock` for real-time status events from Claude Code hooks
- **Shared state file** at `/tmp/unky-mo-state.json` — main TUI writes, sidebar instances read (1s poll). Includes worktree entries with `parent` field.
- **Session status detection** — hybrid approach: Claude Code hooks (primary, real-time) + fsnotify JSONL watcher (reconciliation) + PID liveness checks (cleanup) + `claude agents --json`'s `waiting` + `input needed` / `permission prompt` status (backstop for `question` and `permission` when the hooks are missed, e.g. a dialog open across a TUI restart). Central `status.Manager` is the single source of truth. No time-based heuristics. Status includes a `question` state for sessions blocked on an interactive tool (e.g. `AskUserQuestion`) — **hooks (plus the agents backstop) are the only signals for this status**, since in the JSONL an open dialog's `tool_use` looks like any tool still running. Its *content* is usually in the transcript, though (the `tool_use` line is often written before the dialog opens, but not always: a plan approval, or a call retried after a rejection, can be missing), so `status.ReadPendingTool` recovers a question or permission prompt the hooks didn't deliver, e.g. after a TUI restart (`Manager.RecoverPending`). ExitPlanMode's plan approval isn't reliable: its call is sometimes only written once answered. See `.claude/rules/session-detection.md` for the hook-payload-parsing gotcha this surfaced (`tool_name`/`tool_input` live nested under `hook_input`, never at the top level — don't trust a top-level field without checking what `status-hook.sh` actually sends).
- **Config** at `~/.config/unky-mo/config.toml`
- **Startup checks** (`cmd/mo/setup.go:startupChecks`) — run before every TUI start (including `ctrl+alt+r`), idempotent, never fatal, results shown in the status bar: writes the embedded hook script + ensures the exact V2 hook set, then (unless `[web] disabled`) ensures the web TLS cert (below), checks whether this machine trusts its CA, and (re)spawns `mo web --addr <[web] addr, default :7890>` in the detached `mo-web` tmux session via `ops.EnsureWebServer`. Always respawning is deliberate — it's how `ctrl+alt+r` after `make install` picks up web changes. Without a `mo web auth set` login, a non-loopback addr is narrowed to `127.0.0.1` (see below). An untrusted CA shows a sticky status-bar line (`stickyStatusMsgEvent`, cleared by a keypress) with this OS's trust command.
- **Web TLS** (`internal/web/tlscert.go`, `tlstrust.go`, `tlslisten.go`; `cmd/mo/webtls.go`) — `mo web` serves HTTPS by default (`[web] disable_tls` opts out; `cert_file`/`key_file` bring your own cert). A local CA (mkcert-style, stdlib only, same on macOS/Linux) is created **once** in `<config dir>/tls/` and never replaced automatically, so devices that trust it stay trusting; the server cert it signs is re-signed when it nears expiry or misses a current name/IPv4 (`web.TLSHosts` — both the TUI and `mo web` compute it from the same startup addr). Plain HTTP on the same port gets a 307 to https (first byte `0x16` = TLS), only for hosts the cert covers. Trust detection: Go's `x509` verify against the system store (macOS: the keychain via Security.framework; Linux: the system bundle, loaded once per process — hence "then ctrl+alt+r") plus, on Linux, Chrome's own NSS db (`~/.pki/nssdb` or `~/.local/share/pki/nssdb`) via `certutil`, since Chrome on Linux ignores the system store. Firefox and phones aren't detected; `mo web tls trust` prints their steps and the CA fingerprint. `mo web tls status|trust|regen [--ca]`.
- **Web dashboard** (`mo web`) — a separate process, not embedded in the TUI. `status.Manager` and the hook socket are owned exclusively by the running main TUI, so the web process never touches either — with one write-only exception: "Restart mo" (dashboard header and chat nav, `POST /api/restart`, `Restarter` in `deps.go`) sends `{"type":"mo_restart"}` (`notify.NotifyRestart`, also what `mo restart` sends) to the socket, which the TUI handles exactly like ctrl+alt+r. A socket message rather than injected keys, since a TUI filter or text input would swallow `M-C-r`. The restart respawns `mo web` too, so the browser polls `GET /api/boot` until the process's boot id changes, then reloads. Session status comes from the shared state file, and the dashboard's own lists (sessions/projects/PRs/tickets) are plain-polled from the browser. The per-session **chat view** is pushed, not polled: it live-tails the session's JSONL transcript (reusing `status.Watcher`'s fsnotify-on-directory mechanism, independent of `status.Manager`) over SSE, and a prompt box injects text into the real session via a literal-mode `tmux send-keys` (multi-line text, e.g. a review, via a bracketed `paste-buffer -p`) (gated on the session's state-file status being `idle` *or* `question` — the latter lets you answer a pending `AskUserQuestion` from the browser, surfaced as a banner above the composer from the state file; `permission` stays rejected here, since a permission prompt is answered through its own banner instead, see below). The web is a **full stand-in for the TUI, destructive actions included**: project details list each checkout's live + recent sessions, and the dashboard can start a session, resume one, create a worktree and launch in it, and stop a session (`POST /api/projects/{name}/sessions`, `DELETE /api/sessions/{windowID}`). It can also remove a worktree and/or delete a branch, and move a session into a new worktree (`POST /api/projects/{name}/cleanup` and `/lift`, `handlers_worktrees.go`; the TUI's `x` and `w`). A live session in the worktree, or uncommitted changes at a lift's source, comes back as a 409 the browser turns into the TUI's confirm menu. When the primary window is busy, the launch returns 409 + choices, which the browser shows as the TUI's switch / replace (park) / run-alongside menu before re-posting. These call the same `ops.*` functions as the TUI, with `NoSwitch` set so the attached tmux client isn't moved (`focus: true` opts back in). The browser never sends a cwd or a command: the cwd comes from project + branch, and the command from the configured `[[agent]]` key. That's injection safety, not a capability limit. Optional HTTP basic auth set via `mo web auth set` — stored as a username + salted PBKDF2-SHA256 hash in `~/.config/unky-mo/web-auth.toml` (0600, never plaintext); `web.BasicAuth` wraps the whole server and caches successful logins in memory so dashboard polling doesn't pay the KDF each request. `mo web` refuses a non-loopback `--addr` without a login configured, since the prompt box can drive a live agent. See `internal/web/`. (An earlier PTY-attach terminal-mirror design was tried and removed — it required resizing the user's real shared tmux pane to fit the browser window, which was a disliked side effect; the chat view replaced it entirely.)

## Key Packages

- `cmd/mo/` — CLI entry point (Cobra). Each `RunE` builds an `ops.Context` and calls an `ops.*` function — thin wrappers by design.
- `internal/ops/` — **Domain operations shared by CLI and TUI.** `Context` + interfaces (`TmuxClient`, `ClaudeReader`) + functions. No bubbletea types here — plain functions, testable against gomock fakes.
- `internal/tui/` — Main Bubbletea TUI (app.go model, styles, delegate, keys). Each `tea.Cmd` closure is a 5-line adapter over an `ops.*` call.
- `internal/tui/sidebar/` — Compact sidebar TUI for tmux panes. Has its own `TmuxClient`/`ClaudeReader` interfaces since it runs in a separate process and needs a different method subset.
- `internal/tmux/` — tmux command wrapper (sessions, windows, panes, popups, splits). Adapted into `ops.TmuxClient` by `ops.NewTmuxClientAdapter`.
- `internal/claude/` — Session detection (live + historical), JSONL parsing, hook management. Adapted into `ops.ClaudeReader` by `ops.NewDefaultClaudeReader`.
- `internal/status/` — **Session status state machine.** `Manager` receives hook events + fsnotify JSONL changes + PID liveness signals. Single source of truth for active/idle/permission/question status. `Watcher` monitors JSONL files via fsnotify. `ReadJSONLStatus` reads JSONL tail without time-based heuristics. `ParseHookPayload` handles both V2 unified and legacy hook formats — `PreToolUse`'s `tool_name`/`tool_input` must be unmarshaled out of the nested `hook_input` blob (status-hook.sh forwards Claude's stdin JSON wholesale there), not read as top-level fields. `isInteractiveTool` special-cases tool names known to block on a human choice (currently just `AskUserQuestion`) into `StatusQuestion` instead of the default `StatusActive`.
- `internal/exec/` — `Commander` interface + gomock mock. Shared shell-out seam used by `internal/github` and `internal/gitfiles`; `ops.Context` also carries one.
- `internal/gitfiles/` — A checkout's file contents for the editor tabs (`content.go`: `Resolve` path containment, `ReadFile`, `ReadHEAD` via `git cat-file`, 2 MB cap, binary/non-UTF-8 detection), and its changed files (`git status --porcelain=v2 --branch -z` + `git diff HEAD --numstat -z`, plus line counts for untracked files), its full file list (`git ls-files`) and its upstream ahead/behind, for the web chat view's Files panel. `log.go` reads the Git log tab's history (`GetLog`: `git log --topo-order --decorate=full`, scope `branch` = HEAD + upstream + default branch, or `all`; unpushed = `rev-list HEAD --not <upstream>`, or `--not --remotes` without one) and one commit's files and blobs (`GetCommit`, `GetCommitFile`, against the first parent). A commit is only ever named by a full hex id that `cat-file -t` says is a commit, and a commit file only by a path that commit changed. `selection.go` serves the Git log's commit selection: `ResolveSelection` checks that a set of commits is consecutive (one newest commit, exactly one boundary parent, `rev-list base..head` equal to the set; otherwise a typed `SelectionError`: gap, merge, root or heads) and `GetOverviewRange` reads the change between two commits, `GetOverviewWorktree` from a commit to the working tree (with untracked files), and `HeadCommit` gives HEAD's full id. Pure `-z` parsers plus `Commander`-driven fetchers that always run at the repo root, since a session's cwd may be a subfolder. The sidebar still has its own older parsing in `sidebar/model.go`.
- `internal/tickets/` — Provider-agnostic ticket model + `internal/tickets/jira/` Atlassian Cloud provider (uses `/rest/api/3/search/jql`, NOT the removed v2 endpoint).
- `internal/web/` — HTTP/JSON dashboard + chat view (`mo web`). Scoped interfaces (`StateReader`, `ProjectLister`, `WorktreeReader`, `PRClient`, `TicketSource`, `PromptSender`, `SessionHistory`, `SessionOps`, `GitFiles`, `ChangeAnalyzer`, `CallGrapher`, `Terminals`, `Shells`, `ClaudePane`, `Subagents`, `SlashCommands`, `Restarter`) mirror the `ops.Context` pattern — `SessionOps` is a thin adapter over an `*ops.Context` for launch/resume/park/sibling/worktree/stop/cleanup/lift (`handlers_sessions.go`, `handlers_worktrees.go`), mocked under `internal/web/mocks/`. Small TTL caches (`ttlCache`) decouple browser poll frequency from rate-limited `gh`/Jira calls. The chat view's `transcriptCursor`/`transcriptHub` (`transcript.go`) tail a session's JSONL file and fan out new messages verbatim (as raw JSON) to SSE subscribers, plus `{type:"link", uuid, parentUuid}` stubs for lines they don't forward, so the frontend can walk the conversation tree and show only the active branch (an edited/resubmitted prompt leaves the old branch in the file; parallel tool results hang off earlier assistant lines and stay visible). Beyond that the backend stays schema-agnostic; the frontend (`static/chat.js`) owns all interpretation of the JSONL shape (text/tool_use/tool_result/diffs). The Files panel (`static/files.js`, `handlers_files.go`) polls `/api/sessions/{windowID}/files` and `/tree`, which resolve the checkout from the state file's `path` (never from the request). Clicking a changed file opens a diff tab, and a file in the tree a file tab (see the editor tabs below). The third tab, Git log (`static/graph.js`), polls `/log?scope=` (ETag = body hash, so unchanged polls are 304s). `layoutGraph` assigns lanes in the browser, and each row draws its slice of the lines as an inline SVG, with an "Uncommitted changes" row on top of HEAD. Clicking a commit expands its message and files (`/commits/{hash}`). A file opens a read-only `commit` editor tab (`/commits/{hash}/file?path=`, before/after from git's object store), which has no save, review comments or polling. "Mention in prompt" puts `short ("subject")` into the composer. Ctrl/Cmd-click toggles a commit (or the "Uncommitted changes" row, which can only go with a run ending at HEAD), Shift-click selects from the last clicked row (Ctrl+Shift adds), ↑/↓ walk the rows (with Shift, selecting), Esc clears. A bar above the rows names the selection and offers "Show in Overview", disabled while `selectionProblem` (the server's consecutive rules over the log's parents) finds a problem (plan: `docs/plans/commit-selection.md`). The **Overview** tab (`static/overview.js`, `handlers_overview.go`, `gitfiles/overview.go`; plan in `docs/plans/change-overview.md`) is pinned after Chat in the editor strip and shows the shape of the branch's whole change: `GET /overview?base=branch|head` diffs the merge base with the default branch (`defaultBranch`, as the Git log tab uses) — or HEAD — against the working tree, with untracked files. Each file gets a kind (`gitfiles.Classify`: logic, test, generated, docs, whitespace-only via `diff -w`, pure rename) and an area (`AreaOf`). How the tab lays all this out (header, sections, map, inspector, Review list) is described further down. A file opens a `bdiff` editor tab: a diff tab whose left side is `/file?rev=base`, which the server resolves to its own cached merge base (the old path for a rename); the browser never names a revision. `listedPath` also accepts paths the branch overview lists (a file deleted in a branch commit). A third mode, **Selected (N)** (`?base=commits&commits=<full ids>`, never stored as the tab's mode), shows the Git log selection: the server resolves the ids once (`selectionCache`, 10 minutes; malformed → 400, not consecutive → 422 with the reason, unknown → 404) and serves `OverviewRange`, which `/architecture` and `/calls` analyze like a ref target. Commits never change, so the tab doesn't poll in that mode, and it hides the trace, the scope check and the strip above the composer. Its files open read-only `range` editor tabs (the ids in the tab's `hash`), whose sides are `/file?rev=sel-base|sel-head` for paths the selection changed. With the uncommitted changes selected too (`&worktree=1`, commits optional), the server checks on every request (HEAD cached 2 s) that the commits end at HEAD (422 `worktree` otherwise) and serves `OverviewWorktree` from the selection's base. The tab then keeps polling, and files open editable `sdiff` tabs: a diff tab whose base side is `rev=sel-base` and whose working copy is the plain `/file`, both reads carrying the selection, so a file only the selection lists (deleted in a selected commit) is still served. `ttlCache` drops expired entries once it holds more than 128 keys, since selections make keys unbounded. `GET /excerpt?path=&line=[&end=][&side=new|old][&ctx=]` (session and reviewer prefixes, same `?base=` modes; plan: `docs/plans/overview-explorer.md`) serves a few lines of one file as the change shows them: `gitfiles.Annotate` reads the whole file as `+`/`-`/` ` rows from the overview's `Rev` to its `Head` or the working tree (one `git diff -U<huge>`; untracked, deleted and unchanged files are read directly), and `Cut` slices it by either side's line numbers. The path must be one the change lists (a rename's old path too) or one in the new side's tree. Annotations are cached in `excerptCache` by the revisions, plus a working-tree file's size and mtime (`gitfiles.Stamp`). `GET /architecture` (same modes) runs `internal/review` over the cached overview (plan: `docs/plans/architecture-languages.md`). `static/overview-model.js` holds the tab's pure code (no DOM): the intent trace, treemap and graph layouts, and the explorer's entity model. `buildModel` turns `/overview`, `/architecture` (with `fileUnits`, each changed file's unit), `/calls`, the trace, the scope check and reviewed ticks into entities (`pkg:`, `file:`, `fn:`, `call:`, `imp:`, `con:`, `find:`, `prompt:`), and the `ov*` queries (`ovRelated`, `ovWhere`, `ovVerdict`, `ovChecks`, `ovCaveats`, `ovChips`, `ovReviewQueue`, …) read it. It's unit-tested in Node (`internal/web/jstests/`, run by `go test` through `jstest_test.go`, skipped without `node`). `/calls` loads whenever the tab is visible. `createOverview` also returns `model()` (rebuilt only when an input changed) and `selection`, the explorer's selection store: a history (`selPush`/`selBack`/`selForward` in the model file, kept per target in sessionStorage `mo.overview.sel.<key>`), the hovered entity and the map's Focus, with subscribers. Alt+←/→ go back and forward, and Esc leaves Focus and then clears the selection. The tab is one scrolling page (`pageHead`, `section` in `overview.js`; plan: `docs/plans/overview-explorer.md`). The header has the mode switch and compare line, yellow notes (stale base + Fetch, fallback, truncated), the verdict sentence (`ovVerdict`, phrases select their target), chips and a Caveats list; once something is selected it shrinks to a sticky strip. Then four collapsible sections, Map, Footprint, Intent (chat view) and Scope, each with a one-line summary (`ovSectionSummaries`). A selection opens its section (`ovSection`), collapses the others and scrolls there; a head click overrides that until the next selection. While the Overview shows, the chat view is in Overview mode (`.chat-shell.is-overview`, from `createOverview`'s `onVisible`). The nav widens to 340px with a compact session list, and holds the inspector (`static/inspector.js`): a nav bar (Back / Forward, breadcrumbs, Clear) over the selected entity, or "Start here" (the kinds bar and `ovChecks`) with nothing selected. Switching session keeps the Overview open. Each entity type has its view in the inspector (function, call, import, file, package, contract, finding, prompt, file × prompt cell). It shows chips and alerts, signature before/after, code blocks read from `/excerpt` (`overview.excerpt`, cached per overview ETag, with Diff / File), related lists whose call sites show their line with Peek, the prompts that explain a change, and actions: Focus, Diff, File, Mention in prompt, Ask Claude to fix (`ovFixPrompt`, drafted, never sent), Jump to prompt. In Overview mode the Files panel shows Review / Changed / Branch files / Git log (`files.js` `setOverview`, `static/reviewqueue.js`). Review is `ovReviewQueue` (Needs eyes, Contracts, Logic to read with reviewed ticks, folded Tests / Docs / noise), following the Footprint's area and kind filters. Related rows are marked and the rest dimmed. j/k (↓/↑) step, x ticks, o / f open. Ticks live in localStorage `mo.overview.reviewed.<key>` as `{path: reviewSig}`, so a file that changes loses its tick; the header shows "Reviewed X of Y". The Map section (Packages view) is `static/overview-map.js`. Package boxes sit in layer rows (`ovLayoutMap`: layers ordered by import depth, `Rules.Order` for ties, boxes wrapping to the width), each listing its changed functions (callers first) and the context ones, capped at 12 rows. Boxes fold by hand, past 60 changed functions, or (Fold unrelated) when the selection doesn't touch them. Imports run between boxes and calls between rows (only calls that break something until something is selected, or with All calls), and what the hover or selection relates to stays lit. Clicking a row moves the focus there; Exit or Esc leaves. Across the sections, parts select entities rather than opening diffs (a double-click still opens the diff). It shows as "Probably Bash in prompt N" in the file inspector and the matrix.   - **Analyzers** (`language` in `lang.go`): Go (`goarch.go`, packages), Rails (`ruby.go`, `app/*` layers, constants resolved by Zeitwerk naming), Node (`node.go`, folders below `src`/`app`/`javascript`/`packages`, imports resolved through relative paths, tsconfig paths, package.json imports, workspaces and importmap), Python (`python.go`, packages), Kotlin/Java (`kotlin.go`, `module/package-level`), Swift (`swift.go`, SwiftPM targets or `Features/<feature>/<layer>` folders).
  - **Units are path-like names.** Ruby and Swift edges are inferred from names (`Edge.approx`, dotted in the graph).
  - **Caching:** languages whose references resolve against the tree implement `twoPhase`, which caches raw references per blob id (`index.symbols`) and resolves them per analysis.
  - **Rules:** the repo's `.unky-mo/architecture.toml` layers plus built-in presets (`rails`, `node`, `android`, `ios`) that apply automatically when their stack is detected unless the file sets `presets`. Each preset judges only its own language's units. Path segments are globs (`*`, `ui-*`, `**`), longest match wins, and the repo's own layers win ties. unky-mo has its own rules file. `Analysis.UnitLayers` names the layer of every unit the analysis mentions (packages and both ends of edges, each with its own language), and `Rules.Order` lists the layer names in the rule set's order, which is not top to bottom: the Overview map orders rows by import depth and uses it for ties. `CallGraph.UnitLayers` does the same for every function's unit in `/calls`, whose context functions are often in units `/architecture` never mentions.
  - **Call graph** (`review/calls.go`, `review/gocalls.go`, `handlers_calls.go`; plan: `docs/plans/call-graph.md`): `GET /calls` (session and reviewer prefixes, same `?base=` modes) is the change one level down from units. It lists the functions the change adds, removes, renames (same body, same unit) or changes (body, or `signature`), the calls they gain and lose, one hop of callers and callees, and findings (`removed-called`, `signature-callers`, `untested` within 2 hops). A changed function a test reaches carries `testedBy` (the nearest test; `rootTest` walks up from a test-file helper to the test that calls it, kept as `via`), and a `signature` change carries `sig`/`oldSig`, each version's definition header read as text (`defHeader`: annotation lines skipped, cut at the body), so every language gets it the same way. A function's ID survives file moves (Go: `types.Func.FullName()` minus the module prefix). Call kinds are `static`, `dynamic` (through an interface, drawn to the interface method, with `impl` edges to the implementations found by a cached method-name index), `ref` (a function used as a value, e.g. a handler passed to the mux) and `approx`. Unresolved calls are counted, never guessed. Go is exact: each version's changed packages, their direct importers and the changed packages' tests are type-checked from source with `go/types`, reading from the index, with every package outside the module replaced by an empty one (no toolchain needed; about 0.1% of in-module calls lost). The loader honours build tags via `build.Context` hooks and breaks import cycles (an unguarded cycle recursed until a fatal stack overflow). A commit's index (`newIndexAt`, also the base side) reads files with batched `git cat-file --batch` (`gitfiles.ReadBlobs`, through `Commander.OutputStdin`) instead of three processes per file; `edgeDelta` and the Kotlin/Swift indexes prefetch the same way. `/calls` is cached by `fingerprintCache`: a key's result is kept while the change's file list and (for a checkout) the changed files' sizes and mtimes stay the same, concurrent misses share one computation, errors are kept 10 s. In the browser, the Map section's **Packages | Functions** switch (`mo.overview.archView`) swaps the package map for `static/calls.js`: changed functions in the middle grouped by unit (collapsed to unit boxes past 60; a unit's header toggles it open and closed and counts its new and removed calls in green/red, collapsed or not), callers left, callees right, `ref` edges dashed, `dynamic` with an open arrowhead. Interface implementations are listed in the detail panel ("Implementations" / "Implements"), not drawn. Clicking a node selects the function in the Overview (`onSelect`), so the inspector in the left rail shows its code, callers and callees; the view itself draws no detail any more (it still can without `onSelect`). Findings are listed under it, with `untested` folded. The graph's scroll box is kept across renders and its position restored after the page re-renders (`restore`), as the Map does, and a selection only scrolls the page when it opens another section. `/calls` is polled on its own (`loadCalls`), so a slow graph never holds up the rest of the tab. `removed-called` findings join the tab badge and `#overview-strip`. `editor.reveal(path, line, kind)` opens a file/diff/bdiff tab at a line, and a diff opened at a line is built without collapsed unchanged ranges (`tab.expanded`), so the line can't be folded away. The Overview's violation and contract links pass their lines now too. A function's detail names the conversation turn that last changed it (`turnForRange` in `overview.js`: the intent trace keeps each `Edit`/`Write` result's `toolUseResult.structuredPatch` hunks, shifted by later edits above them; a `create` covers the whole file). Go references passed next to a string literal (`mux.HandleFunc("GET /x", s.handleX)`) carry it as the call's `label`, shown in the detail and by `mo calls`. The other languages are **heuristic** (`review/hcalls.go`): a scanner per language (`hLang.scanFile`, cached by blob id + extension, so it must not depend on the rest of the path, and run on all cores by `index.symbolsMany`, so it must not touch shared state) reads definitions with their own-lines body hashes (a class doesn't change when a method does), call sites (`recv.name(`, refs passed as values), import bindings and class bases from comment/string-blanked code. A per-version `hResolver` (definitions by file and name, class chains via `method`, imports) and the language's `resolve` turn calls into IDs. Every edge is `approx`. A call that matches no single definition is unresolved; it's counted only when the name is defined in the repo or an import says it should be, and its `want` IDs (or `~name` for an unknown receiver, only when no method of that name is left) let a removed function still be found as called. Per language:
  - Python (`pycalls.go`): indentation scopes, self/cls/super through bases, aliases, package re-exports, `__init__` for constructors.
  - JS/TS (`jscalls.go`, language "node", only where `nodeLang` detects a project): imports through `resolveSpec`, including re-exports 2 hops deep (`hFile.Exports`/`Reexports`); default exports; JSX tags and component templates (.vue/.svelte/.astro) as calls; `new` → `constructor`; global receivers and builtin method names never matched.
  - Ruby/Rails (`rbcalls.go`): block and `end` accounting cross-checked with indentation (the hottest per-line patterns, call chains, block keywords and assignments, are hand-written scanners: `rbChains`, `rbKeywordSpans`, `rbAssigns`); `C#m` / `C.m` IDs, with singleton-side bases for `extend` and concerns' `class_methods`; callbacks and `validates … if:` as refs; ERB/HAML views (`view:<path>`) resolving against `app/helpers` and `helper_method`s; `Const.new` → `initialize`; unknown receivers never guessed.
    - **Rails** (plan and notes: `docs/plans/rails.md`).
    - **Routes:** `rails_routes.go` parses `config/routes.rb` (and `draw`n files) like ActionDispatch: `resources`, nesting, `shallow`, concerns, named-route rules. The surface diffs routes by `VERB path`. Through the `hExtra` hook (`rbroutes.go`), routes become `<route>` definitions calling their action, and URL helpers (`route:x`, displayed `x_path`) definitions that `x_path`/`x_url` calls resolve to.
    - **Stimulus:** `stimulus.go` reads `data-controller`/`data-action`/`data-*-target` from views and components, and links them to the JS controller's methods and `static targets` (`hFile.Targets`). `crosscalls.go` is the cross-language pass: it fills context nodes from other languages' sets and matches removed functions and targets against every language's wants.
    - **ActiveRecord typing** (`rbtypes.go`, `rbrails.go`): receivers are kept as chains (`@ticket.event`) and typed left to right through finders, relations, scopes, associations, instance variables (per class, inherited, applied to the controller's views), block parameters, `delegate`, `enum`, AASM, factories and `db/schema.rb` columns (`rails_schema.go`). Synthetic members (`<kind>name`) are entry points with the ID a real method would have. `hExternal` ("-") marks a framework call on a known type: neither drawn nor counted.
    - **Implicit calls:** jobs (`perform_later` → `#perform`), mailers, Pundit (`authorize`/`policy_scope`/`policy(x)`), action → implicit template, `render` and partials (relative names, `render @items`), ViewComponent, Turbo broadcasts.
    - **Tests:** Minitest `test "…"` / spec blocks are definitions. A request test reaches an action through its route helper, since route hops are free in `reachedByTest`. `rbtests.go`'s `testsFor` gives each source file its conventional test files (`hTests`): a function they call by name counts as tested, and a changed file whose test file exists but didn't change gets the `test-not-updated` hint.
    - **Findings:** `route-without-action` and `stimulus-unbound` (red, raised through `hFlagger` when the caller or the files it names changed). `removed-called` also catches callers of a renamed function's old name.
  - Kotlin/Java (`jvmcalls.go`): package-level visibility without imports, extension functions (receiver in `hDef.Class`), companion members, `<init>` for constructors, variable types from declarations to resolve `repo.load()`, overloads merged.
  - Swift (`swiftcalls.go`): one module per SwiftPM target (the rest is one app module), extensions anywhere in the module, protocol requirements with `impl` edges to conforming types (`swiftCallLang` post-processes `hCalls`).
  - Shared rules: a pseudo-definition's name starts with `<` (`<module>`, `<top>`, `<view>`, `<main>`), and such definitions, class bodies and Go's `init` are entry points that are never flagged `untested`. `hDef.Req` hashes only the parameters without defaults, so `signature-callers` fires only when callers must change. The unknown-receiver fallback (`uniqueMethod`) skips names collections and strings share (`commonMethods`). `mo calls` (`cmd/mo/calls.go`, `review/callsfmt.go`) prints the same graph as text (changed functions by unit, their `+`/`-` calls, caller counts, findings), JSON, or Graphviz dot. `--fail-on` exits 1 for chosen finding kinds. The working tree's `index` drops the blob id of files modified since staging (`git ls-files -m`): their staged blob id would otherwise serve a stale cached scan.

It also returns the contract surface: exported Go API diffed by types-only signature, plus routes (Go mux, Express, Rails routes and controller actions, file-based Next/Astro/SvelteKit pages, Flask/FastAPI/Django, Retrofit), CLI flags, config keys, env vars, dependency manifests (go.mod, package.json, Gemfile + lock, pyproject/requirements, Gradle + version catalog, SwiftPM/XcodeGen/Podfile), migrations, and permissions (Android manifest, iOS privacy keys and entitlements). These are found by regex on comment-stripped text, with `git grep` dropping names that only moved. `Overview.baseFetched` is when `origin/<default>` was last fetched; past 7 days the tab offers "Fetch" (`POST …/fetch-base`). The edges are drawn on the Map (red = breaks a rule, also counted on the tab's badge), and the surface is listed in the Review list's Contracts and the inspector. The browser sends the trace's prompts and files; the server keeps only files the overview lists (bounded counts and lengths), fetches the ticket named in the branch (`[A-Z]+-\d+`) itself, adds diff excerpts for files changed outside the conversation, and runs `claude -p --tools "" --strict-mcp-config --setting-sources project --no-session-persistence --output-format json --json-schema …` in the OS temp dir. Verdicts (`in_scope`/`drift`/`unclear`) are tagged on files, kept per window in localStorage with a staleness signature, and "Ask Claude to split these out" drafts (never sends) a prompt. The **reviewer view** (`/branch?project=&branch=` or `&pr=`; `branch.html`, `branch.js`, `handlers_branch.go`) shows the same tab for any branch or PR from the dashboard (Overview links on checkouts and branches, Review on PRs), with no live session. Its API is `/api/projects/{name}/branches/{branch}/…` or `/pulls/{n}/…` (overview, architecture, file, PUT file, tree, scope). The server resolves the target in one of two ways:
  - **Checkout:** the branch is checked out (`checkoutPath`). It's served like the chat view: editable, with uncommitted changes.
  - **Ref:** a commit, read-only (`fileResponse.readOnly`, PUT → 405). For a branch that's its local head (a remote-only branch is fetched). For a PR it's `refs/pull/<n>/head`, fetched together with the PR's base branch and compared with it (`gitfiles.ResolvePR`, `GetOverviewAt`; `review.Analyze` reads `Overview.Head`).
  - Fetches are cached 5 minutes and serialized (`fetchMu`).
  - `editor.js`/`overview.js`/`review.js` take a target (`setTarget({key, api, …})`; `setWindow(id)` is the chat view's shorthand). With no `chatPanel` there's no Chat tab, `transcript: false` hides the trace, and review comments can be copied, or sent only to the branch's live session (`targetView.sessionWindow`). `/api/state` also fills in the `branch` of live rows the TUI left empty, because the TUI only records branches for strays and the sidebar renders the field whenever it's set. The terminal drawer (`static/terminal.js`, `handlers_terminals.go`) lists a window's terminals: the pane named by its `@mo_drawer_pane` option (shown in the tmux drawer), plus every pane parked in its `mo-terms-<instance>` session (`ops.TermSessionName`).
  - It mirrors the selected one with `tmux capture-pane -e`, which never attaches or resizes. The capture and the cursor position are read in one tmux command (`tmux.CaptureScreen`), and `terminal.js` turns the SGR colour escapes into styled spans (`--ansi-0`…`--ansi-15` tokens, 256-colour and truecolour inline).
  - **Live keys** (the default with a keyboard; toggle "Line input"/"Live keys", remembered in localStorage `mo.termLive`): every keystroke goes to the shell, so its own Tab completion, suggestions (fish, zsh-autosuggestions) and Ctrl-R work in any shell. An offscreen textarea takes the keyboard: printable text comes from its `input` event (so layouts, dead keys and IMEs work), other keys are mapped to tmux key names. `POST …/terminals/{pane}/keys` takes `{keys: [{text}|{key}]}` or `{paste}`. Key names must be in `liveKeyNames`, and text may hold no control characters (those are keys). A paste goes in as a bracketed paste with no Enter. The answer is the screen right after, and keystrokes typed meanwhile are batched. The browser keeps Ctrl-W/T/N.
  - **Line input** (the default on touch devices) types one line at a time via literal `send-keys`, and has a Ctrl-C button.
  - tmux reads an argument's trailing `;` as a command separator, even after `--`. So literal sends put trailing semicolons in as hex (`send-keys -H 3b`), and paste buffers are loaded from stdin (`load-buffer -`), never through `set-buffer`'s argument.
  - Option 2, not built: real-time output by streaming a control-mode client (`tmux -C attach -f ignore-size`, which doesn't resize the window) into xterm.js. Keys would still go through `/keys`.

  - The drawer's top edge is a drag handle (`.term-drawer__handle`, pointer events, so touch works too): it sets the output's height (`--term-h`), clamped so the transcript keeps 120px. Double-click toggles between the default 160px and the tallest height, and arrow keys resize it when it has focus. The height is kept in localStorage `mo.termHeight`. Only the browser's view grows; the tmux pane is never resized, and the 200 lines of scrollback fill the extra room.
  - Every pane-addressed request is checked against that window's terminal list, so the browser can't reach Claude's pane or another window.
  - Claude's own running Bash shells (`claude.ActiveShells`, the sidebar's "Shells" section) appear as read-only `claude: <command>` tabs. They come from `/api/sessions/{windowID}/shells`; output is the tail of the shell's `.output` file, which is only read for a pid that session currently lists.

The chat view's middle column is tabbed (`static/editor.js`): a pinned Chat tab (transcript, composer, terminal drawer), then one editable CodeMirror 6 tab per opened file or diff.
  - Files open from the Files panel's "All files" tree, a file tool card's "Open" (Read/Edit/Write), or quick open ("Open file…" / Ctrl+P over `/tree`). On a phone, where the Files panel is hidden, quick open is the only way in.
  - Diff tabs open from the Files panel's Changed list, or a file tab's "Changes" button. They compare HEAD (`?rev=HEAD`, polled too, so a commit updates the left side) with the working copy, which stays editable and saves like a file tab.
    - The editor pane at 760px or wider gets a side-by-side `MergeView` with ⟵ revert arrows. Narrower panes (a phone) get an inline `unifiedMergeView` with a "Revert" button per change; "accept" is hidden, since that would mean changing HEAD. A revert is just an edit, so Save (hash-checked) writes it, and undo works.
    - A file deleted in the working tree shows HEAD's content read-only.
    - A diff tab is the same tab type as a file tab: `tab.view` is always the editable working copy (a `MergeView`'s `b`), so the save, conflict and draft code is shared.
  - Open tabs are remembered per window in `localStorage` (`mo.editorTabs.<windowID>`).
  - `GET /api/sessions/{windowID}/file?path=[&rev=HEAD]` (`handlers_editor.go`) serves one file, and only one the Files panel lists: in `/tree` (tracked + untracked-not-ignored, so `.env` is out of reach) or in the changes list (covers deleted files). `gitfiles.Resolve` then refuses anything that isn't a clean relative path, and any path through a symlink, even one pointing inside the checkout: it could reach `.env` or `.git/hooks`, and Claude can create symlinks. Reads open with `O_NOFOLLOW`. The response's ETag is the content hash; the visible tab re-polls with `If-None-Match` every 3s and applies changes in place (`minimalChange`, keeps scroll).
  - Saving is `PUT /api/sessions/{windowID}/file` `{path, text, baseHash}`, with the same path rules. `gitfiles.WriteFile` only replaces an existing regular file. It writes atomically (temp file + rename, keeping the mode) and only if the file still hashes to `baseHash`, checked again right before the rename. Otherwise the answer is a 409 carrying the current version, which the tab shows as a conflict banner ("Reload from disk" / "Keep mine and save", the latter re-saving against the new hash). A tab whose file changes on disk while it has unsaved edits gets the same banner instead of a reload.
  - CodeMirror joins lines with `\n`, so a CRLF file is edited as LF and converted back on save (`eolOf`/`toLF`). A file with mixed endings opens read-only rather than have every ending rewritten.
  - A poll that was already in flight when a save started is dropped (`saveSeq`), so it can't put the pre-save text back.
  - Prompts (composer and reviews) have control characters other than newline/tab stripped server-side (`stripControl`). An escape sequence quoted from a file would otherwise act as keystrokes, e.g. ending the bracketed paste early.
  - Unsaved edits are stored as drafts in `localStorage` (`mo.editorDraft.<windowID>\0<kind>:<path>`, keyed by the base hash), so a session switch or page reload restores them; there's no blocking guard. Closing a dirty tab asks first. `beforeunload` only warns if a draft couldn't be stored.
  - CodeMirror is a committed esbuild bundle, `static/vendor/codemirror.js`, exposing `window.CM` (entry: `tools/codemirror/entry.js`, which also maps file names to languages via `languageFor`). Rebuild with `make codemirror` (needs Node) only to bump versions or add exports. Don't load CodeMirror from a CDN: two copies of `@codemirror/state` break it, and the dashboard must work offline.
  - Static files are served by `static.go`: a content-hash ETag + `Cache-Control: no-cache`, and gzip for text files (the bundle is ~720 KB raw, ~260 KB gzipped), prepared once per process.
  - Review comments (`static/review.js`):
    - A "+" in a file or diff tab's gutter (on hover, or on the active line on touch) opens a comment box under that line.
    - Comments are block widgets in a CodeMirror `StateField`, so they move with their line; `review.sync` writes the new line numbers back. They're stored per window in `localStorage` (`mo.review.<windowID>`).
    - "Comments (N)" in the tab strip lists them (named so the Overview's Review tab means one thing). "Send to Claude" posts one multi-line prompt (`formatReview`: `path:line`, the quoted line, the comment) to `/prompt`, then clears them. Like the composer, it only works while the session is idle or waiting on a question; otherwise the 409 shows as "Claude is busy".
    - Multi-line prompts go in as one bracketed paste: `tmux.SendPastedText` does `set-buffer` + `paste-buffer -p` + Enter. Claude Code shows it as "[Pasted text #1 +N lines]" and submits it whole; typed newlines would each submit early. Single-line prompts still use `SendLiteralText`.

The composer (`#prompt-input`) is an auto-growing textarea. Enter sends and shift/alt+Enter adds a line, as in Claude Code, except on touch devices (`pointer: coarse`), where Enter adds a line and only Send sends. Images can be attached (`static/attachments.js`) with the paperclip button, by pasting (a screenshot on the clipboard) or by dropping them on the footer:
  - Each image uploads right away to `POST /api/sessions/{windowID}/attachments` (raw body, `handlers_attachments.go`). `AttachmentStore` (`attachments.go`) sniffs the content (PNG/JPEG/GIF/WebP only, 20 MB cap) and saves it as `~/.cache/unky-mo/attachments/<windowID>/<random>.<ext>` (0600). Files expire after 24h (`Sweep`). Removing a chip sends `DELETE …/attachments/{id}`.
  - `/prompt` takes `{text, attachments: [id…]}`. The browser only ever sends ids, which are resolved under that window's directory. `tmux.SendPrompt` then bracket-pastes each file's path **on its own**, which Claude Code turns into `[Image #N]` exactly as for a file dropped on the terminal. The text follows as a paste with a leading space (Claude Code adds none after the tag), then one Enter. The machine's clipboard is never touched (ctrl+v in Claude Code reads it).
  - In the transcript, a prompt with images is a `user` line whose content is `text` + `image` blocks (base64), followed by an `isMeta` line `[Image: source: <path>]`, which is skipped. `renderMessage` shows the images as thumbnails under the prompt (data: URLs, the same 4-type allowlist, so no SVG) and opens them full size on click (`openImageViewer`).

Typing `/` at the start of the message opens slash-command completion (`static/commands.js`, `handlers_commands.go`). ↑/↓ move through it, Tab completes (leaving a space for arguments), Enter completes and sends (on phones it only completes), and Esc closes it. The list comes from `/api/sessions/{windowID}/commands`, built by `claude.SlashCommands` (`internal/claude/commands.go`) from three sources:
  - Built-ins: a hand-kept `builtinCommands` table, read from the command table in the claude 2.1.289 binary (`strings`-style: `name:"…",description:"…",argumentHint:…`). Re-check it when Claude Code adds commands. `Dialog` marks the `local-jsx` ones, which open an Ink dialog the browser can't drive; they get an "opens in terminal" tag.
  - The session JSONL's `skill_listing` attachments (`names` + `- name: description` content, where a description can span lines). The first one lists every skill and plugin command; later ones add skills that appeared mid-session.
  - `commands/**/*.md` and `skills/*/SKILL.md` under `~/.claude` and every `.claude` from the cwd up to the repo root. Their frontmatter supplies `argument-hint`, and the scan catches `disable-model-invocation` commands, which the listing omits.

While a session is `active`, the composer shows Claude Code's own spinner line (`✻ Booping… (1m 9s · ↓ 3.3k tokens)`). No structured source exposes it (`claude agents --json`, the session file, JSONL and hooks all lack it), so `/api/sessions/{windowID}/spinner` (`spinner.go`) scrapes it from a `capture-pane` of Claude's pane (`<session>:<window>.0`, from the state file), scanning up from the prompt box's top border. The browser (`static/spinner.js`) polls it once a second and animates in between: it cycles the glyph, shimmers the verb, ticks the elapsed time and tweens the token count. There's deliberately no fallback: if the line isn't found (e.g. Claude Code changes its layout), nothing is shown.

The permission mode (manual / accept edits / plan / auto) is scraped the same way, from the footer under the prompt box (`⏸ plan mode on`, `mode.go`), because hooks and the JSONL only record it when an event or prompt happens and shift+tab fires neither. `static/mode.js` shows it as a small chip under the composer and tints the composer in the mode's color. Picking a mode from the chip's menu, or pressing shift+tab in the message box, POSTs `/api/sessions/{windowID}/mode`. The server then presses `BTab` in Claude's pane (`ClaudePane.CycleMode`) and re-reads the footer after each press until it matches. The cycle's members and order depend on the user's settings, so nothing is hard-coded: a mode that isn't reached before the cycle repeats comes back as a 409. Changes are only allowed while `idle`/`active`, because in `question`/`permission` a dialog has the keyboard.

Subagents a session spawned with the Agent tool are shown from `/api/sessions/{windowID}/subagents` (`handlers_subagents.go`, `static/subagents.js`). This matters most for background agents: the parent ends its turn and reads `idle` while they keep working. The data comes from `claude.SubagentReader` (`internal/claude/subagents.go`). It reads `<projects dir>/<sessionID>/subagents/agent-<id>.jsonl` plus its `.meta.json` (type, description, the spawning `toolUseId`, `requestShape: "background"`), and the parent JSONL's `<task-notification>`s. It parses only the bytes appended since the last poll.
  - States: `running`; `waiting` (the agent was told to report via `SubagentHandback` but ended a turn without doing so, so it's waiting on its own background shell); `done` (handed back, or a plain `end_turn` for agents not told to hand back); or a notification's non-`completed` status such as `killed`. A `completed` notification alone doesn't mean done, because it also fires when an agent pauses to wait.
  - The browser shows running/waiting agents in a strip above the composer, adds a status line under each Agent tool card (matched by `tool_use_id`), and opens a dialog that live-streams one agent's transcript (`/subagents/{agentID}/transcript`, through the same `transcriptHub` and `createTranscriptView` renderer as the main chat). The agent id must be in the session's listing, and the file path comes from that listing.

A pending interactive question (status `question`) rides the separate `/api/state` poll instead (the TUI's status manager owns it) — rendered as a banner above the composer, not a transcript message. A captured `AskUserQuestion` is a form there (radio buttons, checkboxes for `multiSelect`, a "Type something" field per question). `POST /api/sessions/{windowID}/answer` (`answer.go`) checks the answers against the state file's pending input (question texts must match, else 409) and drives Claude Code's dialog with keys through `ClaudePane.SendKeys`: a digit toggles a multiSelect row or picks a single-select one, ↓ to "Type something" then literal text, ↓ to Next + Enter, and "1" on the review page that tabbed dialogs end with. Every step reads the dialog back from a capture (`parseDialog`), so a dialog the terminal user moved, or text they already typed, stops it with a 409 instead of sending keys blind. Key behavior was probed against Claude Code 2.1.289; re-probe if the dialog changes. A permission prompt (status `permission`) gets its own banner (`#permission-banner`), filled from `GET /api/sessions/{windowID}/permission` (`permission.go`; plan: `docs/plans/permission-answers.md`), polled every second while the status lasts. The server reads the dialog from a capture of Claude's pane (`parsePermissionDialog`: title, question, numbered rows with wrapped lines joined, the footer's "Tab to amend" and plan file) and fingerprints it (`sig`). It adds the state file's `pending_tool`/`pending_input` only when the dialog is about that call (`pendingMatches`: the command, file name, URL host, or a plan), else the plan file the footer names (only a `.md` directly in `~/.claude/plans`, no symlinks), else the dialog's own preview lines (`dialog.preview`). The banner (`renderPermissionBanner`, content from `static/permission-model.js`, tested in Node) shows the command, the edit as a small diff, the plan as markdown, or the URL, then the dialog's own rows as buttons in its wording. Rows that change more than this call are tagged "changes settings". Yes/No rows with "Tab to amend" have a text field, and the plan's "Tell Claude what to change" is a text box with Send feedback and Approve with this feedback. A digit with focus in the banner picks its row. `POST …/permission` `{sig, row, text, approve}` re-reads the screen and refuses (409, no keys) unless the `sig` still matches. Then it presses the row's digit; or walks the cursor to an amend row, presses Tab, types and presses Enter; or types into the plan's empty text row and presses Enter, or BTab to approve with it. It checks the screen after every key, like `answer.go`. Keys were probed against Claude Code 2.1.289 (captures in `internal/web/testdata/permission/`); re-probe if the dialogs change. Once answered, the transcript's `AskUserQuestion` card shows the answers even while folded (header → chips, typed answers quoted), and opening it lists every option with the picks ticked. Frontend is hand-written vanilla JS/CSS embedded via `go:embed` under `internal/web/static/`, styled after the MoMA design system (tokens in `style.css`), with no build step. The chat view is three columns:
- Left: a session nav that switches in place via `history.pushState`, plus usage meters.
- Middle: the transcript, composer and terminal drawer.

## Testing

- **Always run `make test` (or `go test ./...`) after any code change.** Failing tests are a signal — either the code regressed, or the test encoded a behavior that has legitimately changed. Never skip, delete, or comment out a test without first understanding what it's asserting. If a test is wrong, fix the test; if the code is wrong, fix the code. Do not "fix" a failing test by weakening its assertion to make it pass.
- See `.claude/rules/testing.md` for mock patterns, integration tests, ops testing, and the sidebar testing seam.

## Conventions

- Binary name: `mo`
- tmux session name: auto-detected from current session, falls back to `mo` (configurable)
- Hook marker: `# unky-mo` comment in Claude settings hook commands
- Colors tuned for dark terminal backgrounds (~#14191E)
- All keyboard shortcuts visible in persistent footer bars
- Circular list navigation (wraps top↔bottom)
- `ctrl+r` forces an in-process refresh (re-poll sessions, rebuild detail branches, rewrite state file — no network, no binary reload)
- `ctrl+alt+r` restarts TUI + all sidebars (dev workflow — picks up freshly-installed binary). `mo restart` and the web's "Restart mo" do the same via a `mo_restart` socket message (`Model.beginRestart`). The TUI quits and `syscall.Exec`s itself in place (same PID and pane). Don't go back to running the new binary as a child via `tea.ExecProcess`: that left every old TUI waiting underneath, and quitting brought back the previous one.
- Mouse support enabled automatically on tmux session creation
- `exec claude` used in panes so windows auto-close when Claude exits (pane-exited hook)
- Error messages in TUI persist until keypress; success messages auto-clear after 4s
- Left/right arrow keys switch between panels (dashboard sessions, project detail PRs)
- Always use `make install` (not just `go build`) so `ctrl+r` picks up the new binary everywhere
- `git diff --color=always` for colored diffs in popups (piped to `less -R`)

## Commit Messages

- Lowercase first word, imperative mood ("add", "fix", "use", "make")
- No period at the end
- Short single line, ~50-70 chars
- Jira ticket reference at end when applicable (e.g. `OP-175`)
- Examples: `add sidebar terminal split and popup`, `fix idle detection for stale sessions`
- Never add Co-Authored-By lines
